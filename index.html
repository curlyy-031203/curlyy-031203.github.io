问题 / 洞察

在核桃编程负责学科运营期间，我每周需要为新学生安排 3 次入学测评，每次处理 100–150 名学生。学生数据分散在两个来源——家长填写的问卷、以及课导老师在飞书云文档中的私下预约名单——两份表格只含班级信息，与入学测系统按 5 种班型（A1 / A1' / A2 / A3 / A4）要求的导入模板并不匹配。运营需手动合并两份数据、按班型分拣、再套入系统模板，这个环节耗时、易错、易漏。

假设与决策

我判断这是一个高频、结构化、规则明确的重复劳动，适合用工具替代人工。关键决策是做成网页工具而非脚本或 Excel 公式——因为我希望它不只服务我自己，也能让不会写代码的同事和继任实习生直接在浏览器里上传文件就能用，零使用门槛。工具支持上传两个数据源，自动按 5 种班型拆分为 5 张符合系统模板的表格。

实现

基于 GitHub Pages 部署的纯前端工具，用户上传两份源表即可输出 5 张可直接导入的分班表。上线后曾遇到一个真实问题：飞书云文档导出的 Excel 与问卷平台导出的格式不一致（时间字段的表达方式不同），导致飞书数据无法被正确解析。我定位到差异后修复了解析逻辑，使工具能兼容多种数据源格式。

结果与反思

人工分拣单次约 30–40 分钟，使用工具后降至约 3 分钟，且上线后零差错。按每周 3 次计算，该工具每周节省约 1.5–2 小时的重复劳动。

核心案例 · 02
数据自动化

入学测成绩自动汇总工具

把多个班型的分散成绩，增量合并为统一汇总表——与名单拆分工具构成“数据导入 → 成绩汇总”的完整闭环。

Demo →
问题 / 洞察

入学测的成绩管理与名单导入正好相反：5 种班型的考试成绩从系统中分别导出，形成 5 张独立的成绩表，而运营需要将它们持续汇总进一份飞书云文档的总成绩表中。每次考试后手动逐份录入、核对、增量更新，不仅耗时，且在“只加新数据、不重复、不覆盖旧数据”这件事上极易出错。

假设与决策

我意识到这与名单拆分是同一类问题的另一面——同样是高频、规则明确的数据搬运，只是方向相反。因此我用同样的产品思路做了配套工具：支持上传 5 个班型的成绩表与原飞书汇总表，工具自动识别并只追加新增成绩到原表，输出一张包含全部最新成绩的新汇总表，运营只需复制回飞书云文档即可。关键决策是做“增量合并”而非“全量覆盖”——因为全量覆盖有抹掉历史数据的风险，增量逻辑更安全也更符合真实使用场景。

实现

用 Streamlit + Python 部署为浏览器内可用的小工具，零安装、零配置，便于交接给不写代码的同事。规则参数（成绩档位、班型阈值、重合剔除逻辑）放在配置文件中，业务调整不需要改代码；服务端不写数据库、不落日志，处理完即丢，最大程度保护学生信息。

结果与反思

登成绩与登名单同为每周 3 次、每次 100–150 名学生的高频工作。人工汇总单次约 30–40 分钟，使用工具后降至约 3 分钟。两个工具共同覆盖了入学测项目里最重的两个数据环节。

差异化案例 · 03
研究 × 产品

AI 使用者类型测试

把严肃的学术研究量表，重新设计成用户愿意主动参与的趣味测评——基于硕士论文使用的 UTAUT2 技术接受框架，测出“你是哪种 AI 使用者”。

Demo → GitHub →
洞察

MBTI 把“被调查”变成了“被给予一份关于自己的画像”。

决策

我决定把数据采集的方向掉转过来：保留 UTAUT2 框架的测量维度，但在交付端给用户一份即时反馈——用百分比形式综合呈现“你是什么类型的 AI 使用者”。这样用户获得了关于自己的洞察（参与动机），我获得了符合研究框架的数据（研究价值），从单向索取变为双向交换。

实现与现状

基于 UTAUT2 的几个核心维度构建了测评逻辑与结果画像，目前为可运行的原型。

为什么这个项目对我重要

它处在我能力的交叉点上：懂研究方法（知道量表如何构建与测量）、有产品判断（看懂为什么 MBTI 能赢）、能动手实现。它也代表了我感兴趣的方向——把严谨的研究方法，转化成普通人愿意使用的产品。
